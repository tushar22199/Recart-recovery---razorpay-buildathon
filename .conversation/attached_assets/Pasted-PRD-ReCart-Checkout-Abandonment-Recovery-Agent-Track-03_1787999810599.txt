PRD: ReCart — Checkout Abandonment Recovery Agent

Track: 03 — AI Revenue Recovery
One-liner: An agent that watches Razorpay checkout sessions, detects abandonment/failure in real time, diagnoses why it likely happened, and runs a bounded, auditable recovery sequence to win the payment back.

1. Problem

Merchants lose revenue silently at checkout: card declines, OTP timeouts, network drops, UPI app not opening, price hesitation. Most merchants have zero automated follow-up — recovery, if it exists, is a generic "you left something in your cart" email sent once, days later.

2. Goal

Detect a failed/abandoned Razorpay payment attempt within seconds, classify the likely failure reason, and trigger the right recovery action (retry link, alternate payment method suggestion, discount nudge, WhatsApp/email reminder) — then track whether the money was actually recovered.

3. Users

Razorpay merchants (D2C/e-commerce) who want to plug in a "recovery layer" over their existing checkout without rebuilding it.

4. Core Loop
Detect — Listen to Razorpay webhooks (payment.failed, order.paid timeout, payment_link.expired) on test-mode.
Diagnose — Classify failure using error code + metadata (bank decline, insufficient funds, OTP timeout, UPI collect not accepted, network abort). Simple rules engine + LLM fallback for ambiguous cases.
Decide — Pick one intervention per failure class (e.g., decline → generate fresh payment link + suggest alternate method; timeout → instant retry nudge; repeated failure → human escalation flag).
Act — Auto-generate a Razorpay Payment Link for retry, send via simulated channel (log/email/WhatsApp sandbox), with a countdown/expiry.
Track & Stop — Mark recovered if link is paid within window; stop after N attempts (bounded, no spam) or if user explicitly opts out.
Audit — Every decision (detected → diagnosed as X → action Y → outcome Z) logged and viewable in a dashboard.
5. Demo Dataset

Simulate a batch of ~30-50 checkout attempts on Razorpay test mode with varied failure modes (use test cards for declines, timeouts via simulated delay, etc.) so you can show a before/after recovery rate — this is your headline number for judges.

6. Key Screens
Merchant dashboard: live feed of failed payments → diagnosis → action taken → status (recovered/pending/gave up)
Recovery metric card: "₹X recovered out of ₹Y at risk, N% recovery rate"
Audit trail view: click any transaction, see the full decision chain + timestamps
Config panel: max retry attempts, cooldown period, discount cap (bounding controls — this hits "the bar")
7. Meeting "the bar"
Measured money recovered: show recovery rate % across your synthetic batch, not one cherry-picked case
Stopping rules: max 3 recovery attempts per order, hard stop after 24h, no discount beyond a configured ceiling
Compliant escalation: after max attempts, flag to human, don't auto-discount indefinitely
Audit trail: full log of detect→diagnose→decide→act→outcome per transaction, exportable
8. Tech Stack (suggested, lean for time budget)
Razorpay test-mode APIs + webhooks (Payment Links, Orders API)
Backend: Node/Express or FastAPI to receive webhooks + run the rules/LLM classifier
LLM call (Claude/GPT) only for ambiguous failure classification + generating the nudge copy (keeps "meaningful AI use" visible)
Frontend: simple React dashboard (you can scaffold fast)
DB: SQLite/Postgres for the audit log
